# 实战记录

## 已验证场景

一台原本用于代理的海外 Linux 服务器被改造成单用途 AI 爬虫节点。

为避免泄露基础设施信息，主机地址、SSH 账号、端口、Token、密钥和目标站凭据不记录在仓库。

## 服务器条件

- 2 vCPU
- 2 GB 内存
- SSH 是唯一公网管理入口
- Crawl4AI API 只监听服务器 127.0.0.1:11235
- 本地持久通道使用另一个回环端口转发

## 最终运行形态

- 基于官方 unclecode/crawl4ai:0.9.1 构建派生镜像
- 派生镜像标签：overseas-crawler-full:0.9.1
- 容器内存上限约 1.56 GiB
- shm 512 MiB
- 全局页面并发 12
- 作业 worker 12
- 浏览器每 200 页回收
- API 级和爬虫级固定等待关闭，由调用方按目标站需要控制速率
- 请求体、URL 列表、深爬页数、深度、墙钟、队列和 hook 固定上限在可信入口中取消
- 保留 API Token，API 不暴露公网
- 本地 crawlerctl 版本 2.0.0，提供 configure、status、crawl、batch、site、run 和 api

## Crawl4AI 0.9.1 的完整能力改造

官方 0.9.x 按安全默认值把外部请求配置视为 UNTRUSTED，会拒绝 JavaScript、代理、Header/Cookie 和深爬策略等强字段。

本次单所有者可信部署使用可重建派生镜像完成这些改造：

1. 在 /app/api.py 和 /app/server.py 的外部请求配置装载路径使用 TRUSTED provenance
2. 移除深爬页数、深度、墙钟以及 URL 列表、hook 数量和超时的固定夹断
3. 修正 governor 中 max_body_bytes 为 0 时的语义，使 0 真正代表不设固定上限
4. 目标 URL 抓取失败仍返回可解析的 HTTP 200 结果，由 result.success 和 error_message 表达目标失败
5. 保留服务器自身异常的 HTTP 错误，不把所有故障都伪装成成功
6. 启用 execute_js、内部 URL、按请求关闭 TLS 校验等可信调用能力

这些是 0.9.1 的已验证事实，不是其他版本的固定补丁清单。升级时必须先读迁移说明、OpenAPI、Schema 和源码，再决定哪些改造仍然需要。

## 性能结论

- 每条命令新建 SSH 连接时：
  - 健康检查平均约 2131 ms
  - 热缓存爬取平均约 2935 ms
- 改为持久 SSH 通道后：
  - 健康检查约 472 ms
  - 热缓存爬取约 809 ms
- 同一组 24 页原始 HTML 工作负载：
  - 并发池 12 约 10.77 秒
  - 并发池 16 约 10.78 秒
  - 16 没有收益，因此保留 12
- 单请求 101 个 raw URL：
  - 全部成功
  - 总计约 6.85 秒
- 压测后：
  - 无 OOM
  - 容器重启次数为 0
  - 健康状态正常

结论只对这台 2 vCPU / 2 GB 服务器和该组负载成立。其他机器必须重新找性能拐点。

## 关键经验

- 最大性能收益首先来自持久 SSH 通道，而不是盲目提高并发
- 高级能力必须保留原生 JSON 和任意 API 透传，否则友好 CLI 会变成新的能力上限
- 性能配置必须由同一负载的 A/B 结果决定
- 目标网站失败与爬虫服务故障要分开表达，AI 才能可靠重试和诊断
- MCP 不是必需项；CLI 负责稳定执行，Skill 负责让 AI 知道什么时候和怎样调用
