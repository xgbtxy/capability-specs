# 按真实负载调优浏览器并发 SPEC

## 目标

找到稳定吞吐的拐点，并把结论绑定到机器规格、镜像版本、配置和测试集，避免把一次经验变成无条件常量。

## 1. 固定实验条件

每轮只能改变待测并发参数，其他条件保持一致：

- Crawl4AI 镜像和 digest
- 浏览器版本
- 容器内存和 shm
- URL 顺序和请求参数
- 超时、重试和速率配置
- SSH 通道形态
- 冷启动或热缓存状态

开始前记录：

    docker compose ps
    docker stats --no-stream
    docker inspect CONTAINER_NAME
    free -h
    uptime

## 2. 准备四类固定负载

至少包含：

1. raw 本地负载：使用 raw: HTML 隔离公网、DNS和目标站噪音，主要测 API、队列和处理器。
2. 静态网页负载：测网络、解析、Markdown 和内容过滤。
3. JavaScript 动态网页负载：测 Chromium 页、渲染等待和内存。
4. 深爬或混合负载：测调度、去重、流式结果和长任务稳定性。

测试 URL 应是自有、获授权或公开允许测试的页面。不要用同一目标站的反爬策略代替服务器性能结论。

## 3. 需要记录的指标

每一个并发候选值都记录：

- 总任务数、成功数和失败数
- 总耗时与每秒完成页数
- 平均延迟
- p50、p95、p99 或至少最慢一组延迟
- 容器 CPU 峰值和平均趋势
- 容器内存峰值
- shm 使用或浏览器共享内存异常
- OOMKilled 状态
- 容器 RestartCount 前后值
- 浏览器崩溃、超时和队列错误
- 结果完整性，例如 Markdown 长度、结构化记录数

容器结果检查：

    docker inspect -f "{{.State.OOMKilled}} {{.RestartCount}} {{.State.Health.Status}}" CONTAINER_NAME
    docker stats --no-stream CONTAINER_NAME

## 4. 逐档测试

推荐候选值：

    1, 2, 4, 6, 8, 12, 16

小机器可在出现明显拐点或内存危险前停止继续提高。

每档执行：

1. 应用唯一一个并发变化
2. 重启并等待健康
3. 先跑一次预热但不计入热缓存统计
4. 每类负载至少重复三轮
5. 保存原始结果和汇总
6. 确认无 OOM 和重启后再进入下一档

冷启动实验单独做，不能拿第一轮与后续热缓存轮平均。

## 5. 选择性能拐点

优先选择满足以下条件的最低并发值：

- 下一档吞吐提升已经很小
- p95 或最慢请求没有明显恶化
- 内存仍有系统余量
- OOMKilled=false
- RestartCount 不增加
- 动态页面和深爬结果完整
- 连续压测后健康

如果 12 和 16 的总耗时相同，应选 12，因为更低的资源压力会给复杂页面和偶发峰值留下余量。

## 6. 长时间复测

用所选值执行：

- 至少一个大批量请求
- 至少一个服务器侧深爬
- 重复创建与释放浏览器页
- 一个包含目标失败的混合批次
- 一段足以观察内存爬升的持续运行

浏览器定期回收用于控制长期泄漏。已验证场景使用每 200 页回收，但其他环境要观察内存曲线后确定。

## 7. 已验证参考

在 2 vCPU / 2 GB、容器内存约 1.56 GiB、shm 512 MiB 的场景：

- 全局页面并发 12
- 作业 worker 12
- 浏览器每 200 页回收
- 24 页 raw 负载下，12 约 10.77 秒，16 约 10.78 秒
- 因 16 无吞吐收益，选择 12
- 101 个 raw URL 单请求全部成功，约 6.85 秒
- 压测后无 OOM、无容器重启

此参考用于给测试范围一个起点，不能替代本机实测。

最终结论必须同时写：

- 选择值
- 为什么不选更高值
- 哪类负载是瓶颈
- 机器规格和版本
- 需要重新调优的触发条件
